## what changed from the plan

the dec 19 report laid out 7 phases. the original idea was to build an in-memory HNSW first (phase 2), bolt on basic persistence (phase 3), then add MVCC (phase 4), then concurrent readers (phase 5). in practice over the last month and a bit it was easier to just do them all together, as I found myself planning/designing ahead at each phase anyway. the HNSW algorithm operates directly on the mmap'd persistent storage with copy-on-write semantics from the start, there is no separate in-memory index

## HNSW implementation details

won't rehash the full algorithm here (the paper is goated) but some implementation-specific choices worth noting:

### parameters

```
m = 16              connectivity per node
m_max = 8           upper layer max neighbors
ef_construction = 200  beam width during insert
max_layers = 7      max hierarchy depth
ml = 1/ln(m)        level multiplier (~0.361)
```

these are pretty standard, m=16 is what hnswlib uses as default, the level multiplier `1/ln(m)` comes straight from the paper - it means each node has probability 1/m of appearing in the next layer up, which gives the nice property that layer k has n/m^k nodes in expectation. with m=16 and 100k nodes:

- layer 0: 100,000 (all nodes)
- layer 1: ~6,250 (~6.25%)
- layer 2: ~390
- layer 3: ~24
- layer 4: 1-2
- layers 5-6: effectively empty at this scale

### heuristic neighbor selection

the paper describes two neighbor selection strategies: "simple" (take the m closest) and "heuristic" (prefer diversity by avoiding candidates dominated by already-selected neighbors). initially went with simple to get things working, then switched to the heuristic (Algorithm 4 from Malkov & Yashunin 2016)

the heuristic works by iterating candidates in distance order and skipping any candidate that is closer to an already-selected neighbor than it is to the query. this promotes diversity in the neighbor list: instead of clustering all neighbors on one side of the query, it spreads them across different "directions" in the vector space. the paper explicitly says the heuristic "significantly increases performance" and it matters most for clustered real-world data

the implementation also includes `keepPrunedConnections` from the paper: after the heuristic pass, if fewer than M neighbors were selected (because many were dominated), remaining slots are filled from the discarded candidates in distance order.
the pruning path (when a neighbor's list is full and we need to decide whether to replace the worst) still uses the simpler "replace worst if new is better" approach. a full heuristic re-evaluation of all neighbors at that point would be expensive and the simple replacement is a reasonable approximation.

### soft delete

deleting a vector marks the HNSW node as deleted rather than removing it from the graph. search skips deleted nodes. this avoids having to restructure neighbor lists, which would be expensive and complex (removing a node from the graph requires finding all its neighbors and re-linking them). the downside is space waste - deleted nodes still occupy slots and still get traversed during search (they're skipped but their neighbors are still expanded). a compaction pass could rebuild the index without deleted nodes.

importantly, soft delete preserves the full graph structure - layer assignments, neighbor lists, everything. this is what makes the crash recovery approach work (more on that below).

### per-tag isolation

each vector tag gets its own HNSW index, stored in a separate `.hnsw/<tag>.hnsw.mvcc` file - it makes sense to separate as different tags have different dimensions (you can't compare a 768-dim text embedding with a 128-dim image embedding), and global search across tags doesn't make semantic sense. post-hoc filtering by tag on a single global index would waste most of the search work. this matches how production vector databases handle it (Pinecone namespaces, Qdrant collections, etc)

the HNSW files are lazily loaded into a hashtable (`(string, Hnsw_mvcc.t) Hashtbl.t`) and created on first vector insert for a given tag.

### index size: ~5.8M nodes per tag

the page table is 4MB, storing ~48 bytes of metadata plus an array of 8-byte page offsets. that gives ~524K page offsets. at 11 nodes per page, the maximum is ~5.77M nodes per index.

this was originally 64KB / ~80K nodes, which was pretty awful especially considering the academic paper use case from the proposal (1M+ vectors),, bumped the page table to 4MB which is the simplest fix that adequately covers the target workloads. the 4MB is reserved virtual address space - actual I/O per commit is proportional to `page_count`, not the reserved size, so a mostly-empty index doesn't pay for the full 4MB
if we ever needed 50M+ nodes, a two-level page table (page table -> chunk pages -> data pages) would be the next step, but 5.8M is enough for now I hope!!!!

### int32 neighbor IDs

neighbor slots store int32 slot IDs rather than int64. this halves the storage per neighbor (32 x 4 = 128 bytes for layer 0 instead of 256 bytes). the max slot ID is ~2 billion, which is way more than the page table can hold anyway, saves meaningful space

## the persistence layer

### file layout

```
superblock (4KB):     magic, version, active page table pointer, params, CRC32
page table A (4MB):   epoch, metadata, page offset array, CRC32
page table B (4MB):   shadow copy for atomic swap
data pages (4KB each): 11 HNSW nodes per page (372 bytes each)
```

total header: ~8MB. data pages follow, appended as needed.

### copy-on-write mechanics

writes never modify existing pages, when a node needs to be updated (e.g. a neighbor was added):

1. check if this page was already copied in the current transaction (hashtable lookup)
2. if yes: modify the copy in place
3. if no: copy the 4KB page to a new location, modify the copy, track as dirtyS

### transaction overlay

during a write transaction, newly inserted nodes live in an overlay hashtable (`(int, node_data) Hashtbl.t`). this is separate from the dirty page hashtable. the overlay serves two purposes:

1. **read-your-writes during insert**: when inserting node B, the algorithm can see recently-inserted node A as a potential neighbor, even though A hasn't been committed yet
2. **deferred serialization**: nodes are built in memory as structured records, only serialized to page format on commitS

### dual page tables and commit

the two page tables enable atomic commit without a write ahead log, with commit sequence:

1. flush overlay nodes to dirty_pages (serialize to page format)
2. allocate physical space for dirty pages (append to the data region)
3. write all dirty pages to their allocated positions in the mmap
4. build new page table with updated offsets for modified pages
5. write new page table to the *shadow* slot (whichever of A/B is not currently active)
6. msync to ensure all data and the shadow page table are durable
7. write the active_root pointer in the superblock to point to the shadow (now the new active)
8. update superblock CRC32
9. msync again

the commit point is step 7. before that, a crash leaves the old page table active and everything is consistent. after step 7, the new page table is active with all changes. a crash between step 7 and step 9 (stale superblock checksum) is handled by tolerating stale checksums as long as at least one page table has a valid CRC32.

### why CRC32

CRC32 is used on the superblock and both page tables. it's there to detect corruption, not for security. the specific use case is: on file open, verify that the active page table is intact. if it's not (e.g. crash during write), try the other page table. CRC32 is fast, well-understood, and sufficient for this purpose. considered just using an incrementing counter (if it's odd, write was interrupted) but CRC32 also catches bit rot and partial writes.

### epoch-based reader isolation

readers snapshot the active page table at `begin_read` and continue seeing that version even if a writer commits during their read. implemented with reference counting:

```
begin_read: lock epochs mutex, copy active_table, increment epoch refcount, unlock
end_read:   lock epochs mutex, decrement epoch refcount, remove if zero, unlock
```

the epochs_lock mutex is the only lock in the system. write serialization is provided by LMDB's single-writer guarantee - whoever holds the LMDB write transaction is the only writer, so no write lock is needed in the HNSW layer. this was a deliberate simplification: rather than having separate LMDB and HNSW write locks (which would risk deadlocks and add complexity), I lean on the fact that all HNSW writes happen inside an LMDB write transaction. one lock to rule them all

if I ever want to do HNSW-only operations (like compaction) without holding an LMDB transaction, i'd need to add write locking. but for now, coupling to LMDB's write path is simpler

## cross-store crash consistency
this is the part i'm most interested in from a correctness standpoint. we have two stores that must agree: LMDB (source of truth for graph data, vector metadata, slot mappings) and the HNSW MVCC file (the index). each vector operation commits to both. the commit sequence is:

```
1. begin LMDB write transaction
2. stage LMDB changes (vector metadata, slot mappings)
3. commit HNSW (epoch increments, pages written, pointer swapped)
4. store new HNSW epoch in LMDB metadata
5. commit LMDB transaction
```

HNSW commits before LMDB. this ordering means: if LMDB commits (step 5 succeeds), HNSW definitely already has the changes (step 3 already succeeded). the only inconsistency window is when HNSW committed but LMDB didn't (crash between steps 3 and 5).

### why HNSW commits first

the alternative (LMDB first, HNSW second) is worse: if LMDB commits but HNSW crashes, LMDB has slot mappings pointing to HNSW slots that don't have the expected data. reconciliation would need to either re-insert into HNSW (expensive, requires the vector data which is in the vector file) or remove from LMDB. the current ordering means HNSW always has *at least* as much data as LMDB, and reconciliation only needs to mark excess HNSW data as deleted (cheap).

### detection: O(1) epoch comparison

after each HNSW commit, the new epoch is stored in LMDB metadata within the same LMDB transaction. on database open it compares:

```
hnsw_epoch = read from HNSW file
lmdb_epoch = read from LMDB metadata
```

if they diverge then an evil crash must've happened, need to reconcile

### reconciliation: O(n) scan

LMDB is the authoritative source of truth (it didn't commit, so it reflects the pre-crash state). reconciliation makes HNSW match LMDB:

1. build a set of valid slot IDs from LMDB's `hnsw_slots` map for the tag
2. scan all HNSW nodes:
   - non-deleted node with no LMDB entry -> orphan from crashed insert -> mark deleted
   - deleted node with LMDB entry -> incomplete delete from crashed txn -> un-delete
   - non-deleted node with LMDB entry -> consistent, skip
3. fix the entry point (find the highest-layer non-deleted node)
4. commit the HNSW changes
5. sync the LMDB epoch to match HNSW

soft delete is super cool here and makes this reconciliation way faster, since it preserves the full graph structure. un-deleting a node restores it to exactly its original state in the graph, same layer, same neighbors, same connections, no re-insertion needed

this also handles multi-operation transactions correctly. if one LMDB transaction contained "insert A, delete B" and crashed after both HNSW commits but before LMDB commit: HNSW has orphan A and deleted B, LMDB has no A and still has B. reconciliation marks A deleted (orphan) and un-deletes B. the entire transaction is atomically rolled back from HNSW's perspective.

the reconciliation is idempotent: if the system crashes *during* reconciliation, it re-runs on next open, finds the same discrepancies (or none if the HNSW commit within reconciliation succeeded but epoch sync didn't), and converges.

### why not a WAL?

a write-ahead log would provide true atomicity - prevent the inconsistency rather than detect and fix it. but a WAL adds per-transaction overhead (write the log entry, fsync, then do the actual work, then clean up the log). the epoch approach has zero overhead in the normal case (just an integer stored alongside other LMDB metadata) and O(n) cost only after actual crashes. for an embedded database where crashes are rare, this tradeoff makes sense.

a WAL would also add file management complexity (log rotation, compaction, recovery replay). the epoch approach is ~60 lines of code in the orchestration layer, with no changes to the HNSW MVCC layer itself.

## known limitations and future work

### no benchmarks yet

this is the biggest gap. i have no recall@k numbers, no latency measurements, no comparison against brute force or hnswlib!!!

### no compaction / unbounded file growth

both the vector file and HNSW files grow forever - deleted vectors dont free up their space in the vector file, and same with deleted HNSW nodes. old COW pages are also abandoned (no free list or page reclamation). a database with heavy churn (many inserts + deletes) will waste space over time. compaction would require rebuilding the HNSW index and rewriting the vector file, updating all cross-references in LMDB.
